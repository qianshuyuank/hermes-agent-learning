# Hermes Human-Agent Collaboration Guide Design Spec

## 1. 核心理念 (Philosophy)
* **定调**：人类是交响乐团指挥 (Orchestrator)，Hermes Agent 是专业的乐手/执行者 (Specialized Worker)。
* **目的**：文档旨在明确边界，确保 AI 成为力量倍增器，而不是制造混乱的源头。AI 负责执行具体实现、验证假设和搜集信息，人类负责架构决策、质量把控和纠偏。

## 2. 人类职责与最佳实践 (The Human Orchestrator)
* **任务发起**：提供高信息密度的上下文。不仅要说明“做什么”，还要指出“约束是什么”以及“相关入口文件在哪里”。
* **架构把控**：核心数据结构、模块划分、API 契约等高阶设计必须由人类确认后，Agent 才可开始编码。
* **审查标准**：Review Agent 的代码时，不仅看逻辑对错，更要检查边界处理、安全限制以及是否符合当前项目的极简/过度设计标准。
* **干预与刹车**：当发现 Agent 陷入“死循环调试”或方向明显跑偏时，必须及时终止，并用更明确的指令纠正方向。

## 3. Hermes Agent 的职责 (The AI Worker)
* **谋定而后动**：在提问或采取破坏性行动前，必须主动通过工具读取本地代码库，掌握现有模式。
* **小步验证**：严格遵循 TDD 或渐进式开发。写一段代码即运行测试/验证，禁止积累大面积未验证代码。
* **暴露不确定性**：遇到需求模糊、有多个合理选项时，停止自行猜测，向人类发起明确的澄清请求 (使用 Clarify)。
* **经验沉淀**：任务完成后，总结遇到的坑和解决路径，主动固化为 Skill 或长效 Memory。

## 4. 权限与红线 (Permissions & Hard Boundaries)
* **代码合并限制**：Agent 生成的代码应处于独立分支或直接由人类 Review 确认。禁止未经允许直接向 `main` 等保护分支 push 代码。
* **高危操作确认**：凡涉及删除不可恢复数据、修改核心基础设施配置的终端操作，必须经人类显式授权。
* **非静默原则**：对于长时间运行的后台任务，任务结束或失败时必须显式通知用户，不允许静默失败。

## 5. 切换与交接协议 (Handoff Protocols)
* **Agent -> 人类**：交接时必须说明当前状态：“已完成 X，在 Y 处遇到 Z 报错，建议人类检查文件 W 的权限”。
* **人类 -> Agent**：接管任务时，提供断点上下文：“接手 feature-x 分支，修复最新 commit 中 test_auth.py 的报错”。

## Scope Check
本设计文档针对 `hermes-agent-learning` 仓库的团队协作文档建立。范围明确，不涉及系统代码逻辑修改，仅涉及文档内容的创作与规范。

## Ambiguity Check
无模糊项，已确认采用“基于角色的指南”结构，符合用户需求。
